# Patient Management Dashboard | Technical Implementation

Version: 2.0 · Date: 2026-11-11 · Status: implementation baseline for the reduced scope.

This version replaces v1.1. The product and UI/UX documents are aligned, so conflicts no longer require cross-document override rules. React + Express + MySQL and server-side pagination remain, with simpler search, updates, caching, and operations. S01–S06 are implemented: shared rules, database/API, patient workspace, unsaved-change protection, a Chromium lifecycle test, and Express static hosting. See README for actual commands and verification scope, and the [implementation plan](superpowers/plans/2026-11-11-patient-workspace.md) for task order.

## 1. Architecture and technology stack

```text
React UI → fetch /api → Patient Controller → Patient Service → Patient Store (Drizzle) → mysql2 → MySQL
```

| Area | Choice and boundary |
|---|---|
| Project tooling | Retain npm workspaces, TypeScript, and Vite; no additional build platform |
| UI | Tailwind CSS + local Button/Sheet components, with Sheet based on Radix Dialog; native form controls and SVG icons exported from Figma; only components actually used |
| Forms | React Hook Form + Zod resolver; one form shared by creation and editing |
| Requests | Native fetch + TanStack Query for query state, submission, and invalidation/refetch |
| Backend | Express 5, organized into patient Module / Controller / Service / Store responsibilities with manual dependency assembly |
| Storage | MySQL 8.4 LTS + Drizzle ORM + mysql2/promise; local Docker Compose |
| Testing | Existing Vitest and Supertest; React Testing Library for form tests as needed; one Playwright lifecycle test |

Retain apps/web, apps/api, and packages/shared. The shared package contains only browser-safe schemas, types, date rules, and state constants; it exports no database drivers or environment variables. Do not introduce a global state library, search service, generic migration framework, or dependency injection container.

The patient module in `patient.module.ts` creates PatientService and injects it into `patient.controller.ts`; the app mounts its Router. The Controller handles Zod validation, HTTP statuses, and responses. The Service generates IDs, reads records after writes, and handles save-result errors. `patient-store.ts` handles only Drizzle queries, writes, and row mapping. This follows NestJS-style responsibilities with explicit constructor injection, without NestJS or decorators.

## 2. Data model

Use one patients table with flat address columns and a nested address in API responses. The backend generates UUID v4 IDs. Name and DOB combinations have no uniqueness constraint.

| Column | MySQL type | Rules |
|---|---|---|
| id | CHAR(36) PRIMARY KEY | Generated by the backend |
| first_name / last_name | VARCHAR(100) NOT NULL | Trim; preserve original case |
| middle_name | VARCHAR(100) NULL | Normalize empty values to NULL |
| date_of_birth | DATE NOT NULL | 1000-01-01 through the current UTC date |
| status | ENUM('Inquiry','Onboarding','Active','Churned') NOT NULL | Independently validated by the backend |
| address_line1 / address_line2 | VARCHAR(200) NOT NULL / NULL | Second line is optional |
| city | VARCHAR(100) NOT NULL | Trim |
| state / country | CHAR(2) NOT NULL | Enumerated state code; country is US |
| postal_code | VARCHAR(10) NOT NULL | ZIP / ZIP+4 string |
| created_at / updated_at | DATETIME(3) NOT NULL | Database UTC_TIMESTAMP(3) |

Use InnoDB, utf8mb4, and utf8mb4_0900_as_ci. The primary key is sufficient initially. Do not predefine multiple indexes for a few hundred demonstration records or claim that a regular index accelerates `%keyword%`. No search helper columns, separate address table, or schema_migrations table.

`packages/backend/sql/schema.sql` remains the table-creation baseline. `apps/api/src/module/patients/patient-table.ts` maps existing columns with Drizzle and infers row types; both must stay synchronized when fields change. This stage does not use drizzle-kit, push, or automatic migrations, and does not alter existing database structures. Writes use field objects and search uses parameterized expressions; only LIKE ESCAPE and UTC_TIMESTAMP remain controlled SQL fragments.

Infer input types from Zod. POST and PUT share a complete-form schema, retaining createPatientSchema. Required fields cannot be omitted. Omitted optional fields, empty strings, whitespace, and null normalize to null; omitting an optional field in PUT clears it. Reject unknown fields and client-specified id/createdAt/updatedAt. Keep the API model:

```ts
type Patient = CreatePatientData & {
  id: string;
  createdAt: string;
  updatedAt: string;
};
// CreatePatientData: firstName, middleName, lastName, dateOfBirth, status, address.
// address: line1, line2, city, state, postalCode, country.
```

Retain real-calendar validation and UTC display logic, changing the lower bound to the year 1000. mysql2 uses dateStrings: true; Drizzle DATE uses string mode, so DOB always returns YYYY-MM-DD. The database writes DATETIME in UTC; Drizzle reads it in date mode, then toISOString serializes it to a UTC string. Never convert DOB into a local-time instant before formatting.

## 3. API contracts

| Endpoint | Input | Success response |
|---|---|---|
| GET /api/health | None | 200 `{ data: { status: 'ok' } }`; confirms process responsiveness only |
| GET /api/patients | search, status, page | 200, paginated response |
| GET /api/patients/:id | UUID | 200 `{ data: Patient }` |
| POST /api/patients | Complete form | 201 `{ data: Patient }` |
| PUT /api/patients/:id | Complete form | 200 `{ data: Patient }` |

No PATCH or DELETE. PUT updates an existing record; missing records return 404 rather than being upserted. Complete updates use last-write-wins semantics, with no guarantee of preserving fields changed concurrently by another user.

### 3.1 List queries

```ts
type PatientListQuery = {
  search: string;                  // Default ''; at most 100 code points after trimming
  status: 'All' | PatientStatus;    // Default All
  page: number;                    // Default 1; positive integer, maximum 2147483647
};
type PatientListResponse = {
  data: Patient[];
  pagination: { page: number; pageSize: 20; total: number };
};
```

Accept only these three query parameters, validating before constructing SQL. Arrays, objects, repeated parameters, and unknown parameters return controlled 400 responses. Page size is fixed at 20; clients cannot supply pageSize or sort. total means the count after combining search + status filters. Do not return counts, totalPatients, or totalPages; the UI can calculate page count from total.

Treat the entire trimmed search input as a single keyword, OR-match the three name fields, then AND the status condition. No tokenization, NFKC normalization, or search columns. Case and accent comparison follow utf8mb4_0900_as_ci; no additional Unicode equivalence rules are promised.

```sql
WHERE (first_name LIKE ? ESCAPE '!' OR middle_name LIKE ? ESCAPE '!' OR last_name LIKE ? ESCAPE '!')
  AND status = ?
ORDER BY last_name ASC, first_name ASC, id ASC
LIMIT ? OFFSET ?
```

Omit the name condition for empty search and the status condition for All. Escape `!`, `%`, and `_` as `!!`, `!%`, and `!_` before wrapping the keyword in `%`. Bind every value through execution parameters rather than concatenating user input; only validated conditions control SQL structure.

COUNT and page queries reuse the same WHERE conditions and parameters. Execute ordinary SELECT statements separately, without a read-only snapshot transaction. Concurrent writes may briefly cause inconsistencies between reads; the next refresh resolves them. This is an explicit limitation. Out-of-range pages return the requested page number and an empty array without automatic correction or a frontend synchronization loop. With no matches, page=1 returns total=0; higher page numbers remain unchanged, and the UI offers a return-to-first-page action.

### 3.2 Writes and errors

Create with one INSERT. Edit with one UPDATE replacing all editable fields, retaining created_at and updating updated_at. Each InnoDB statement is atomic, so no explicit write transaction, read lock, or field merging is needed. SELECT by ID after writing and return the database record. If the record is absent after an update, return 404; do not infer absence from changedRows=0 alone, since unchanged submissions must also succeed.

The read after writing is not guaranteed to share a snapshot with the write. If the write succeeds but reading fails, do not report definite failure to save. Return SAVE_RESULT_UNAVAILABLE, ask the user to check the list before retrying, and do not automatically repeat the write.

Consistent error shape:

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "Check the highlighted fields.", "fieldErrors": { "address.postalCode": ["Enter a valid ZIP code."] } } }
```

- 400: Invalid JSON, ID, or query parameters.
- 422: Form validation failure; fieldErrors uses dotted paths.
- 404: Patient or API route not found.
- 413: Request exceeds the 32KB express.json body limit.
- 500: Unclassified server error; use SAVE_RESULT_UNAVAILABLE when a successful write cannot be read back.

Use one final error middleware. Let Express 5 handle asynchronous rejections without a generic async wrapper. A network interruption or SAVE_RESULT_UNAVAILABLE means the save result requires verification; the frontend retains input and asks the user to check the list. Logs contain only necessary error types, not complete patient content, SQL parameters, or credentials.

## 4. Frontend state and interactions

- React local state manages search input, committed query conditions, page number, and panel mode. TanStack Query manages server data.
- Separate query keys into `['patients', 'list', query]` and `['patients', 'detail', id]` to prevent list/detail collisions.
- fetch checks response.ok; GET forwards Query's AbortSignal. Debounce search by 300ms and return to page 1 on search/status changes. Do not retain the previous query's page as placeholder results.
- Update list conditions together. A status change uses current input and cancels pending debounce so an old condition cannot reappear later. No URL state synchronization.
- Keep reads simple: disable automatic refetch on window focus, provide manual Retry on GET failure, and never retry writes automatically.
- Initialize forms only when entering create/edit mode; background data changes must not reset input. Submit complete forms without a difference calculator.
- After a successful write, update current details from the returned record, switch to detail mode, and invalidate list queries. Creation returns to page 1; editing stays on the current page. No optimistic updates, manual list insertion, or count recalculation.
- Do not refresh that patient's details in the background while editing. Use Query cancellation for in-flight GET requests when needed; do not add request sequence numbers or a cache coordination framework.
- Handle saving and list refresh separately. A failed refresh offers only a list retry; details continue to show the saved record.
- The panel has only closed/create/detail/edit modes. Cancel, close, and Escape all close it; the form backdrop does not. One confirmation dialog handles dirty forms, without a PendingExit model or beforeunload registration.

See the [UI/UX document](ui-ux-design.md) for layout, fields, and copy. Creation/editing opens details immediately after success, eliminating matchesPatientFilters and persistent View patient notifications.

## 5. Database initialization and delivery

- Retain the lockfile and Node/npm version constraints. Use the verified MySQL 8.4 image documented in README.
- One Compose MySQL service persists development data, with two local schemas: pmd_local and pmd_test. Two services or an automatic database creation/destruction framework are not required.
- Provide `packages/backend/sql/schema.sql` and `packages/backend/scripts/init-db.ts`, which executes only that fixed table-creation file. Initialize explicitly with `db:init`; do not alter tables during API startup or write a generic migration version manager. CREATE TABLE IF NOT EXISTS makes repeat initialization non-destructive; it does not migrate existing tables.
- `packages/backend/scripts/seed.ts` inserts approximately 25 synthetic examples covering page 2, all statuses, empty optional fields, and long content. Do not clear the database or generate benchmark data. Fixed sample IDs allow repeated runs to skip existing records.
- Inject database credentials through environment variables inaccessible to the frontend. Test connections allow only local pmd_test, and cleanup affects only that database. Do not reuse development data. Retain target validation without a multi-level cleanup authorization system.
- Local demos use a non-root account limited to these two schemas. A separate migration account or permissions acceptance matrix is not required. Configure production networking/TLS/account management for the environment if public deployment is actually needed.
- After building, Express can host Vite static assets on the same origin. The frontend requests relative /api paths only. The single workspace lives at `/`, without a routing library. Unknown /api routes return JSON 404.
- Keep .env out of Git. Do not add analytics, telemetry, external fonts, or address lookup requests. Use synthetic data only; public release is not required in this delivery.

## 6. Testing boundaries

Retain the existing testing tools and update tests that conflict with the new contracts. Do not retain obsolete functionality to preserve test counts. Focus on:

1. Shared rules: required/optional fields, enums, real dates and range, ZIP, complete updates, and query parameters.
2. Real MySQL + Supertest: create/read, complete updates, invalid input not stored, search/filtering across pages, 404, and successful unchanged submissions.
3. A few form tests: error mapping, disabled controls while saving, input retention after failure, and dirty exits. Do not test component-library internals.
4. One browser lifecycle test: create → view → edit → search/filter → refresh. Supplement with one manual desktop/360px, keyboard, and post-save refresh failure check.
